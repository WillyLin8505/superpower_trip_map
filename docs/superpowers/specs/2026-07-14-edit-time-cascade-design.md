# 編輯時間即軟錨點 + 鄰居讓位 Design Spec

**日期：** 2026-07-14
**Lane：** Manager / TASK-023（排程互動模型改寫）
**產品發現：** 使用者回報「自動調整卡片之間的時間有誤」;經 root-cause 調查 + AUQ 定案(前後對稱、保留交通時間),使用者已確認理解正確。

## 1. 問題 / 根因（已用測試驗證）

目前排程是**鎖定驅動**:`lib/utils/clientScheduler.ts` 的 `recalcDay` 只把「被鎖住(start/end)」的卡片當錨點,**沒鎖的卡片每次都用「當天開始 + 累積停留/交通」重算 start**。

現有測試 `__tests__/client-scheduler.test.ts` 證實:
```
p1.startTime = '15:00'（未鎖 start）→ 重算後變回 '09:00'
```

因此使用者調整一張「沒鎖」卡片的開始時間 → `recalcDay` 立即用當天起點重算蓋掉 → 開始時間彈回。但 UI(`CardContent.tsx`)在未鎖時卻顯示可編輯的時間選擇器 → 編輯無效、看似「自動調整有誤」。

## 2. 目標

不需先手動鎖,**編輯一張卡片的開始(或結束)時間,那個值就成立**,鄰近卡片的停留/結束自動讓位對齊。直覺化,保留既有的三鎖(start/duration/end)作為硬錨點。

## 3. 產品決策（定案）

- **DEC-601 軟錨點：** 編輯某卡片的開始或結束時間 → 該卡片對「本次重算」成為錨點(其被編輯值固定),不需手動點鎖。
- **DEC-602 調整優先序 結束 > 停留 > 開始：** 需要自動調整一張卡片以讓位時,先動它的**結束時間**,其次**停留**,最後才是**開始**。使用者剛設的開始/被編輯值最受保護。
- **DEC-603 對齊保留交通：** 讓上一張卡片的結束對齊下一張卡片的開始時,**保留交通時間**:`prev.end + travel(prev→next) = next.start`。
- **DEC-604 反轉夾住(clamp)：** 若對齊會使某卡片 `end < start`(負停留)→ 夾住為 `end = start`、`durationMin = 0`。
- **DEC-605 前後對稱：** 開始時間「往後移」與「往前移」都要對稱處理(往前移時前面卡片同樣讓位、後面卡片跟著往前)。
- **DEC-606 顯式鎖優先：** 使用者手動點的三鎖(`startLocked`/`durationLocked`/`endLocked` 及其衍生鎖)仍是**硬錨點**,優先於本次編輯的軟錨點;遇到硬鎖鄰居時以夾住處理,不覆寫鎖住的值。

## 4. 行為（worked examples）

被編輯的卡片本身:保留新開始 + 保留停留 → **整塊平移**,結束 = 新開始 + 停留(DEC-602:動結束、保開始/停留)。

```
往後移：A 09:00–10:00 → B 10:00–11:00 → C 11:00–12:00（travel 皆 0）
把 B 開始移到 10:30：
  B → 10:30–11:30（整塊平移）
  A 結束對齊 B 新開始（保留交通）→ A 09:00–10:30（A 保開始、停留拉長）
  C 往後跟隨 → 11:30–12:30
若 A 開始也 ≥ 10:30（無法對齊）→ A 夾住：10:30–10:30、停留 0（DEC-604）

往前移（對稱）：把 B 開始移到 09:30：
  B → 09:30–10:30
  A 結束對齊 B 新開始 → A 09:00–09:30（A 停留縮短）
  C 往前跟隨 → 10:30–11:30
```

含交通:`prev.end + travel = next.start`(DEC-603)。例如 A→B travel=15,B 開始 10:30 → A 結束 = 10:15。

## 5. 範圍

- **`lib/utils/timeEdit.ts`：** 由「單卡片編輯」擴充為「編輯 + 鄰居讓位」的純函式(輸入整段 places + 被編輯 placeId/field/value,輸出新 places)。保留舊 `applyTimeEdit` 或以新函式取代。
- **`lib/utils/clientScheduler.ts`：** 讓被編輯卡片在該次 `recalcDay` 被視為錨點(軟錨),使既有 backwards/forwards 排程據以 cascade;調整緊鄰前一張卡片的規則為「保開始、縮/放停留使結束對齊(DEC-603)」而非現行的「平移其開始」,並加入 DEC-604 夾住。
- **`app/itinerary/ItineraryClient.tsx`：** `handleTimeChange` 改呼叫新的 cascade 函式(呼叫點;TASK-022 已完成、此檔已解鎖)。
- **不改：** 三鎖 UI 與 `lockDerive.ts` 語意;交通時間計算;AI 重排。

## 6. 與現有鎖系統的關係

- 顯式鎖(DEC-606)仍是硬錨點,`isTimeAnchored` 行為不變。
- 「編輯即軟錨」只作用於**本次重算**,不寫入 `*Locked` 欄位(不改變鎖 UI 狀態)。
- 一段內若同時有硬鎖與軟錨,硬鎖優先;軟錨的 cascade 在硬鎖邊界內進行,超出即夾住。

## 7. 錯誤 / 邊界

- 被編輯卡片是**第一張**:沒有前一張可對齊,只平移自己 + 往後 cascade。
- 被編輯卡片是**最後一張**:只影響前一張對齊 + 自己平移。
- 對齊後某卡片停留 0 → 顯示 0 分(DEC-604),不可為負。
- 跨越多張都無法容納 → 逐張夾住為 0。
- `travel` 為 null 視為 0。

## 8. 測試（TDD，皆為新增,不改既有測試語意）

1. **往後移(無鎖、無交通)**:編輯中間卡片開始 → 自己平移、前一張結束對齊新開始、後續往後 cascade。
2. **往前移(對稱)**:同上鏡像。
3. **保留交通**:`prev.end + travel = next.start`。
4. **反轉夾住**:前一張無法對齊 → `end=start`、停留 0。
5. **第一張 / 最後一張**邊界。
6. **顯式鎖優先**:鄰居被鎖 → 不覆寫,cascade 夾在鎖邊界。
7. **回歸**:既有 `client-scheduler.test.ts`(純鎖驅動、無手動編輯的情境)全數保持綠。
